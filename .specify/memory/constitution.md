# 바통(Baton) Constitution

## Core Principles

### I. 진료 맥락을 이어받는다

바통의 핵심 가치는 보호자가 바뀌어도 환자의 진료 맥락을 이어받는 것이다.
기능의 우선순위와 완료 여부는 진료 전 브리핑 → 진료 기록 → 진료 후 정리 →
권한 있는 가족의 조회 → 다음 진료 브리핑으로 이어지는 흐름을 기준으로 판단한다.
브리핑에는 지난 진료 이후 바뀐 점과 가족 질문을 제시해야 한다.

브리핑·질문 통합·기록 비교에 사용하는 과거 기록은 같은 환자·같은 진료과로
제한해야 한다. 진료과를 확인할 수 없는 기록은 임의로 분류하거나 다른 과의
맥락에 섞지 않고 확인 대상으로 남긴다. 전체 타임라인 조회와 AI의 진료과별
맥락 구성을 구분해야 한다. 이는 다른 진료의 정보가 섞이는 것을 막기 위한 기준이다.

### II. AI는 근거 있는 정보만 정리한다

AI는 기록의 추출·질문 통합·요약·쉬운 말 표현·기록 연결만 수행한다.
진단, 처방 결정, 검사 수치의 의학적 해석과 치료 권고를 생성해서는 안 된다.
복약 변경과 변경 이유는 원문에 기록된 내용만 전달한다.

모든 AI 출력 항목은 정의된 JSON 스키마를 따르고 원문 참조와 확인 필요 여부를
포함해야 한다. 원문 참조는 음성 구간, 문서·전사 인용 또는 원 질문 ID처럼
사용자가 실제 근거로 돌아갈 수 있어야 한다. 근거 없는 값과 질문 답변은 비워 두고
‘확인 필요’로 표시해야 하며, 낮은 확신도의 값을 확정된 사실로 표시해서는 안 된다.

기록 간 불일치는 AI로 비교 가능한 항목을 추출한 후 코드로 필드별 대조한다.
두 원본과 차이를 함께 제시하고 어느 기록이 옳은지 AI가 판단해서는 안 된다.
미해결 불일치는 다음 브리핑에서도 확인 대상으로 유지한다.
사용자가 값을 바로잡을 때는 원본 근거와 수정 내역을 보존한다.

### III. 환자가 공유를 통제하고 서버가 권한을 보장한다

공유 범위 변경은 환자 본인이 기본이며, 대표 보호자는 환자의 위임이 켜져 있을 때만
대행할 수 있다. 일반 보호자는 자기 권한을 확대하거나 다른 가족의 등급을 조회할 수 없다.
제품의 열람 등급은 ‘일정만·동행·전체 내용’ 3단계를 기준으로 한다.
‘일정만’에는 진료 내용·브리핑·질문 답변을 포함해서는 안 된다.
‘전체 내용’ 권한도 환자의 비공개 메모 열람 권한을 포함하지 않는다.

모든 API는 인증된 호출자와 환자별 구성원 관계를 검사하고, 서버에서 작업 권한과
응답 필드를 제한해야 한다. 화면에서 숨기는 것만으로 권한 검사를 대신할 수 없다.
원문 다운로드·업로드와 비동기 작업 결과 조회에도 같은 권한 기준을 적용한다.
권한 밖 항목과 다른 가족의 등급은 응답에서 제외하고, 화면에 잠금 표시나
‘숨김 N개’로 존재를 드러내서는 안 된다.

비공개 메모는 환자 본인만 접근할 수 있다. 가족 브리핑·질문 통합 등 가족에게
전달되는 AI 처리의 입력에서 제외해야 한다. 의사에게 보여줄 화면에는 환자 본인이
포함을 선택한 메모만 넣는다. 원본 파일은 공개 경로에 두지 않고 권한 검사를 통과한
요청에만 제공한다. 클라우드 저장소를 쓰는 경우 공개 접근을 차단하고 권한 검사 후
발급한 presigned URL로만 접근한다.

동행 등급의 세부 범위는 기능 명세(`specs/001-baton-mvp/spec.md`)의 열람 범위 허용표로
확정했다. 허용표에 없는 필드와 미정 항목은 전체 내용에만 둔다(2026-10-09 해소).

진료 정리의 공유 시점은 '검토 후 공유하기 확정'이다. 확정 전에는 가족에게 공개하지 않고,
확정 후에도 권한 검사와 ‘확인 필요’ 표시를 유지한다(2026-10-09 해소).

### IV. 누구나 읽고 녹음 상태를 알 수 있다

React 기반 모바일 우선 웹앱으로 제공하고, 대상은 보호자 동행이 필요한 환자 전반으로
정의한다. 사용자 문구는 ‘환자·보호자’로 통일하고 고령자만을 전제로 제한하지 않는다.
환자에게 제공하는 요약은 쉬운 말로 표현하되 약 이름·용량·일정과 원문 근거를 보존한다.

글씨 크기와 고대비 설정은 1단계 필수 기능이며 모든 구현 화면에 적용해야 한다.
큰 글씨에서도 주요 내용과 조작 요소가 잘리거나 겹치지 않아야 한다.
가장 큰 글씨와 고대비를 적용한 상태로 핵심 흐름을 검증해야 한다.

녹음 기능은 환자의 녹음 허용 설정을 따라야 한다. 녹음 중에는 명시적인 문구와
경과 시간을 지속적으로 표시해 색상만으로 상태를 전달하지 않는다.
의료진 동의 확인 화면은 이번 구현에서 제외한다. 이 화면의 제외를 녹음 관련
법적 확인이 끝났다는 근거로 취급해서는 안 된다. 실시간 자막은 선택 과제다.

### V. 핵심 흐름과 검증 가능한 데모에 집중한다

해커톤 구현은 당일에 수행하며, 약 5시간의 개발 시간에서 1단계 핵심 흐름을 먼저
완료한다. 질문 통합·브리핑·진료 정리·타임라인·처방 비교·공개 범위·접근성의
통합 시연을 검증한 뒤 필요한 2단계 기능을 추가한다.

데모에는 가상 환자·시드 계정·모의 문서·가상 음성만 사용하고 가상 데이터임을 표시한다.
실제로 호출한 AI 결과, 저장해 둔 결과, 시드·정적 화면을 시연과 제출물에서 구분한다.
AI 결과는 저장해 같은 입력에서 재사용하며, 입력이 바뀌면 이전 결과를 그대로
최신 결과로 표시하지 않는다. 준비한 음성의 전사 저장본은 실패 시 대체 자료로 쓸 수 있다.

음성 인식·사진 판독·진료 정리처럼 오래 걸리는 작업은 작업 ID와 상태 조회를 제공하는
비동기 처리로 구성한다. 실패 시 완료된 것처럼 표시하지 않고 오류와 재시도 경로를
제공한다. 질문 통합·브리핑도 API 응답 시간 한계에 가까워지면 비동기로 전환한다.

## 제품·기술 제약

- 근거 문서는 `docs/baton_planning_최종.md`다. 이전 기획안은 `docs/archive/`에 역사 자료로 보존한다.
  최신 확정 결정을 이전 초안보다 우선하며, 제안·미정·확인 필요 사항은 상태를 보존한다.
  이 헌장에서 채택한 설계 기준과 과거 팀 합의의 상태를 구분한다.
- 기본 기술 방향은 React, Cognito, API Gateway HTTP API, Lambda, DynamoDB, S3,
  Amazon Transcribe와 Amazon Bedrock이다. 단 이번 가상 데이터 로컬 해커톤 데모는
  `specs/001-baton-mvp/plan.md`에 기록한 승인 예외(로컬 Fastify·SQLite·시드 JWT, AI만 AWS)를 따른다.
  특정 모델의 접근 가능 여부와 성능은 실제 계정에서 확인해야 하며 기획안 표기만으로 검증 완료를 주장하지 않는다.
- 기본 리전은 서울 `ap-northeast-2`다. 데이터 처리 리전과 안전장치의 충돌은
  계획에 드러내고 결정 근거를 기록해야 한다.
  이번 가상 로컬 데모는 Bedrock Guardrails(교차 리전 처리)를 쓰지 않고, 서울 in-region 호출과
  시스템 프롬프트 + 서버 후처리(스키마·근거·제한값 혼입·의료 판단 문구 검사)로 처리한다.
  실제 정보 처리 전에는 한국어 안전성 검증을 포함해 다시 결정한다(2026-10-09 해소).
- 병원 위치는 위치 표시만, 원내 약도는 정적 이미지로 제공한다.
  원내 동선 계산·길찾기·가는 법 안내·돋보기·녹음 동의 확인 화면은 만들지 않는다.
  방문 경험은 참고용으로 표시하고 의료적 판단이나 공식 안내의 근거로 사용하지 않는다.
- 회원가입·해외 진료 번역·푸시 알림·병원 시스템 연동은 이번 구현 범위에서 제외한다.
  사진 판독·직접 녹음·비공개 메모·위임·방문 경험 등은 2단계로 관리한다.
  음성 업로드·전사의 단계가 기능표와 구현 범위표에서 다르므로 기능 명세에 구분해 기록한다.
- Vite, 지도 제공자, 배포 방식과 추가 사용자 역할은 헌장에서 임의로 확정하지 않는다.
  모델·API·데이터 구조의 세부 사항은 기능 명세와 구현 계획에서 결정한다.

## 개발 흐름과 검증 기준

- 기능 명세에는 사용자 흐름, 구현 단계, 역할별 허용 필드, AI 입력과 출력 근거,
  완료 기준을 기록한다. 제안·상충 항목의 결정과 근거를 기록한 뒤 관련 구현에 반영한다.
- 구현 계획은 이 헌장 준수 여부를 점검하고, 제약 위반이나 예외가 필요한 경우
  이유·영향·대안을 기록한다. 작업은 명세와 계획의 완료 기준에 연결한다.
- 핵심 데모는 지난 진료의 보호자 A에서 이번 동행 보호자 B로 이어받는 흐름으로
  검증한다. B에게 브리핑을 볼 수 있는 권한을 부여하고 이름·등급·동행 이력을 통일한다.
- 권한 검증은 화면 확인뿐 아니라 API 직접 호출로 수행한다. 비구성원 접근,
  일정만 응답의 진료 내용 제외, 일반 보호자의 범위 변경 거부, 위임 해제 상태의
  대표 보호자 변경 거부, 보호자의 비공개 메모 접근 거부와 등급 비노출을 확인한다.
- AI 검증에는 근거 없는 질문 답변, 흐린 문서, 다른 진료과 기록, 가족 메모와 약봉투
  불일치를 포함한다. 원문 이동·빈 값·확인 필요 표시와 진단·처방·수치 해석 금지를
  확인한다. 프롬프트나 안전장치를 설정했다는 사실만으로 통과로 판단하지 않는다.
- 모의 자료와 정답 라벨로 추출 정확도·불일치 탐지율을 측정하고, 수정 기능을 구현하면
  사용자 수정률을 기록한다. 기획안의 12장과 약 20장 표기가 상충하므로 평가 계획에서
  실제 자료 수와 분모를 명시한다. 근거 없이 수치나 통과 기준을 만들어 보고하지 않는다.
- 완료 보고에는 검증 결과와 미구현·정적·대체 자료를 명시한다.
  헌장 변경은 로컬에서도 검토할 수 있어야 하며 커밋·GitHub 게시 여부와 별개로 관리한다.

## Governance

이 헌장은 바통의 명세·계획·작업·구현 검토 기준이다. 템플릿의 예시나 기획안의
오래된 화면·API 초안이 이 헌장을 자동으로 대체하지 않는다. 본 문서는 사용자의
프로젝트 원칙 정리 요청에 따라 2026-10-09 최초 작성·채택한다.

개정에는 변경 사유, 관련 기획 결정, 이전·새 원칙, 영향받는 명세·계획·작업과
필요한 전환 절차를 기록하고 프로젝트 담당자의 검토를 거쳐야 한다.
원칙과 충돌하는 구현은 헌장 개정 또는 사유·범위·해소 시점을 명시한 검토된 예외
없이는 완료로 처리하지 않는다. 보안·근거 검증을 우회하는 무기한 예외는 허용하지 않는다.

버전은 `MAJOR.MINOR.PATCH`를 사용한다. 기존 원칙의 제거·호환되지 않는 재정의는
MAJOR, 원칙·절차의 추가나 실질적 확장은 MINOR, 의미를 바꾸지 않는 문구 정리는
PATCH를 올린다. 최초 정식 원칙은 `1.0.0`으로 시작한다. 최초 채택일은 유지하고
내용을 변경한 날에 최종 개정일을 갱신한다.

명세·계획 작성, 작업 완료 및 PR 검토 시 헌장 준수 여부와 남은 TODO를 확인해야 한다.
TODO의 해소는 결정 근거와 영향 범위를 기록하고 의미 변화에 맞게 버전을 갱신한다.
관련 템플릿·명령은 헌장을 실행 시 참조하며, 헌장 개정 명령은 해당 파일들을 수정하지 않는다.
