# 화면 정의(1단계 구현 대상)

**상태**: 2026-10-09 팀 제공 와이어프레임 PDF 반영. 최종 기획안 7장의 화면 번호를 유지하고, 경로·API·범위별 표시·testid에 실제 PDF의 배치를 추가했다. 앱 코드는 아직 없다.
tasks·quickstart의 "25-2", "19번" 같은 번호는 이 표를 가리킨다. [원본 PDF](../../docs/references/baton-ui-wireframe-selection.pdf)와 [25쪽 연결표·조정 기록](../../docs/wireframe-integration.md)을 함께 참조한다. **PDF 쪽 번호와 화면 번호는 다르다.** 설정 25·25-2는 이 선택본에 없으므로 기존 정의를 따른다.

## 공통 규칙

- 모바일 390px 기준, 하단 탭 3개: **홈 · 타임라인 · 설정**. 상단에 기록 주인 칩과 `가상 데이터` 배지를 항상 표시한다.
- 서비스명 표기는 **바통**(부제 '진료 동행 노트').
- 범위 밖 내용은 **처음부터 없는 것처럼** 그린다. 잠금 아이콘·'권한 없음'·'숨김 N개'·흐린 카드 금지. 화면은 응답에 블록 키가 있는지로만 판단하고, 범위 이름으로 분기하지 않는다(응답에 본인 범위 이름이 없다).
- `needsCheck=true` 항목은 값 옆에 `확인 필요` 배지(글자 + 아이콘, 색만으로 구분 금지). 값이 `null`이면 '기록에 없어요'로 표시하고 값을 지어내지 않는다.
- AI 결과 영역에는 출처 배지를 붙인다: `mode=live` → '실시간 AI', `mode=fixture` → '저장된 결과'.
- 작업 진행: '정리하는 중…'(문구 + 스피너) → 실패 시 '정리하지 못했어요' + '다시 시도'. 실패를 완료처럼 표시하지 않는다.
- 글씨 3단계(`normal` 18px · `large` 22px · `extra-large` 26px 기준 본문)와 고대비(흰 배경 #FFFFFF, 검은 글자 #000000, 진한 청록 강조 #00695C, 3px 검은 테두리)를 모든 화면에 적용. 터치 영역 최소 48×48px. 다크 모드로 대체하지 않는다.
- 사용자 문구는 '환자 · 보호자', 쉬운 말. 의료 판단 문구를 화면에서 새로 만들지 않는다.

## PDF에서 반영한 공통 배치

- 기본 화면은 밝은 회색 바탕, 큰 제목, 흰 둥근 카드, 청록색 주요 버튼이다. 기록 주인 선택 칩은 청록, 진료과 선택 칩은 남색, 확인 필요 카드는 연노랑으로 구분한다. 아이콘에는 글자 라벨을 함께 둔다.
- 구현 시작 토큰: 배경 `#F5F6F8`, 카드 `#FFFFFF`, 본문 `#202833`, 보조 글자 `#59636E`, 청록 `#0F766E`, 남색 `#203864`, 테두리 `#DDE2E7`, 확인 배경 `#FFF8E6`, 확인 테두리 `#D5A54C`. 카드 반경 16px, 버튼 14px, 칩 999px, 좌우 여백 20px, 카드 사이 12~16px. **PDF CSS 추출값이 아니라 이미지에 맞춘 구현 시작값**이다. 접근성 확인 후 조정하고 고대비에서는 기존 고대비 토큰으로 교체한다.
- 390px 모바일 한 열, 넓은 화면은 같은 열을 가운데 배치. PDF의 긴 화면 높이를 고정 높이로 복제하지 않는다. 글씨가 커지면 카드·버튼 높이가 내용에 맞게 늘고 칩은 줄바꿈한다.
- 홈·타임라인·설정은 하단 탭 3개를 유지하고, 질문·브리핑·기록·검토 등 상세는 뒤로가기 헤더와 주요 버튼을 둔다. 상단에는 진료 맥락(환자·날짜·진료과·동행자)을 받은 meta로 표시한다.
- 주요 버튼을 하단 고정할 경우 본문에 버튼 높이 + `env(safe-area-inset-bottom)`만큼 여백을 둔다. 키보드가 열린 입력 화면에서는 등록·저장 버튼이 가려지지 않게 하고 고정 높이에 의존하지 않는다.
- 최신 공유 카드의 세로 점·청록 테두리, 옅은 청록 AI 패널, 노란 확인 안내를 재사용한다. 공유 성공·새 기록 배너는 POST share 성공 후 또는 실제 공유본 상태에만 사용한다.
- 데이터는 seed-story.md를 따른다. PDF의 민수·지은·혈압약·3월 동행 A·자리표시자를 그대로 복사하지 않는다. 실제 원본 이미지 확인 없이 정밀한 색·간격 일치를 주장하지 않는다.

## 화면별 상세

### 01 로그인
- PDF 1쪽: 문서 아이콘·서비스명·큰 로그인 제목 → 설명 → 라벨 있는 이메일/비밀번호 → 가로폭 전체 청록 로그인 버튼 → 찾기/가입 링크 → 가상 안내. 시드 계정 빠른 선택은 폼 아래 별도 데모 영역에 추가한다.
- 실패 시 '이메일 또는 비밀번호를 확인해 주세요'(어느 쪽이 틀렸는지 구분하지 않음).
- 로그인 후: 연결된 환자가 있으면 첫 환자의 02, 환자 계정이면 자기 기록 02.
- testid: `login-email`, `login-password`, `login-submit`, `quick-login-<patient|a|b|c>`.

### 02 · 04 홈
- PDF 3·5쪽: 상단 기록 주인 칩 → 진료과 칩 → 기록 주인 제목 → 청록 다음 진료 카드 → 노란 확인 필요 카드(full만) → 흰 가족 질문 카드(companion 이상) → 지난 기록. 선택본의 문서 올리기·해외 요약 카드는 1단계 가족 홈에서 생략한다.
- 다음 진료 카드의 브리핑은 흰 주요 버튼, 병원 안내는 테두리 보조 버튼. PDF의 '병원 약도 · 동선 보기'는 '병원 위치·약도'로 표시한다.
- 기록 주인 칩: `나`(→03) · 연결된 환자 이름들. 진료과 필터 칩(`depts`).
- **다음 진료 카드**(`nextVisit.meta`): 진료과, 날짜·시간, 병원, 이번 동행자. '병원 위치·약도'(→10·11)는 모두에게.
  - `briefingReady` 키가 있을 때만 '진료 전 브리핑 보기'(→09)와 '가족 질문 N개'(→08), '진료 기록하기'(→15).
- **확인 필요 카드**: `openAlertCount` 키가 있을 때만(→19).
- **지난 기록**: `recent[]`를 진료과별로. 카드 내용은 받은 블록만(schedule만이면 날짜·병원·다음 일정만).
- 일정만 홈(PDF 5쪽)은 확인·질문 카드를 만들지 않는다. '예정된 일정'은 받은 `nextVisit.meta`와 `recent[].record.blocks.schedule.nextSchedule`로만 구성하고 중복 일정을 한 번만 표시한다. 별도 예정 일정 API나 준비사항을 추측하지 않는다.
- 홈 가족 질문 개수는 `questionCount`(원 질문 개수)다. 'AI가 2개로 정리했어요'는 HomeRes에 통합 개수가 없어 표시하지 않는다. 질문 화면에서는 통합 2개 + AI 추가 1개를 구분한다.
- 완료 기준: A 로그인 시 확인 필요 1건, C 로그인 시 브리핑·질문·약 정보가 화면과 응답 모두에 없음.
- testid: `next-visit-card`, `briefing-link`, `questions-link`, `alert-card`, `recent-visit-<vid>`.

### 03 내 기록 빈 화면
- PDF 4쪽: 기록 주인 칩과 '내 진료 기록' 제목 아래 안내 아이콘·'아직 내 진료 기록이 없어요'·쉬운 설명·큰 주요 버튼을 중앙에 둔다.
- 일정 등록·문서 올리기·가족 초대는 준비 중 표시를 사용한다. T063·T064 등 선택 화면이 구현된 경우에만 해당 시연 화면으로 연결하고 실제 저장·연결 성공을 표시하지 않는다.
- 하단 탭을 유지한다. 환자 계정의 자기 기록은 02로 열고, PDF 6쪽의 별도 복약 홈은 1단계에 추가하지 않는다.

### 08 가족 질문
- PDF 9쪽: 환자·진료 맥락 → 질문 입력과 추가 버튼 → 작성자 칩이 있는 원 질문 카드 → 옅은 청록 통합 패널 속 흰 질문 카드 → 하단 브리핑 버튼. 원 질문 3개·통합 2개·AI 추가 1개의 개수를 구분한다.
- 질문 입력(1~200자) + 등록. 등록된 질문 목록(작성자 이름·시각).
- 'AI로 질문 정리하기' → 작업 진행 → 통합 질문 목록: 합친 원 질문 번호 표시(예: '질문 1·2를 합쳤어요'), `addedByAI`는 'AI가 추가' 배지.
  - `merged.blocks.full`이 있을 때만 AI 추가 질문 아래 '근거 보기'(basisRefs 인용).
  - `merged.stale=true`면 '새 질문이 있어요. 다시 정리할까요?'.
- '이 질문으로 브리핑 만들기' → POST briefing → 09로 이동.
- testid: `question-input`, `question-submit`, `merge-button`, `merged-question-<id>`, `ai-added-badge`, `basis-<id>`.

### 09 진료 전 브리핑(데모 핵심)
- PDF 10쪽: 뒤로가기·'진료 전 브리핑'·'30초 읽기' 배지, 변경 카드·번호 질문 카드·full 전용 카드·정적 약도 카드·하단 주요 버튼. **PDF 아래쪽 질문을 변경 바로 다음으로 옮긴다.**
- 순서: **바뀐 점**(`briefing.changes`) → **오늘 물어볼 질문**(`questions`) → (full만) **지켜볼 증상**·**먼저 받을 검사**·**준비사항** → 병원 동선 미리보기(정적 약도 썸네일) → '진료 기록 시작'(→15).
- full 블록이 있으면 바뀐 점 각 항목 아래 이유(`changeReasons`)와 '원문 보기'(sourceRefs 인용 펼치기). full이 없으면 이 버튼을 **만들지 않는다**.
- 준비사항 `text=null` → '기록에 없어요 · 확인 필요'.
- 30초 안에 읽히게: 바뀐 점과 질문을 첫 화면(스크롤 없이 390×844)에 둔다.
- 첫 화면 기준은 보통 글씨의 B 시드 브리핑이다. 아주 큰 글씨에서는 스크롤을 허용하고 내용은 생략하지 않는다. full의 긴 이유·원문은 펼치기로 보여주어 핵심 변경·질문을 밀어내지 않는다.
- 병원 안내는 '병원 위치·약도 보기', 주요 버튼은 '진료 기록 시작'. '진료 시작 · 녹음'·계산된 경로라는 표현을 쓰지 않는다.
- testid: `briefing-changes`, `change-<id>`, `briefing-questions`, `briefing-watch`, `briefing-tests`, `briefing-prep`, `source-button-<itemId>`.

### 10 · 11 병원 위치 · 약도(정적)
- PDF 11·12쪽: 병원명·진료과 → 병원 위치/원내 약도 탭 → 그림 → 번호가 있는 안내 순서 → 참고 경험 카드. PDF의 같은 층 4단계 대신 시드 hospital.json의 실제 가상 안내(접수·채혈·내과·수납·건물 밖 약국, 5단계·여러 층)를 사용한다.
- 탭 '병원 위치': `map.svg`(가상 지도 그림, 병원 핀), 주소(복사 버튼), 전화(`tel:` 링크). 길찾기·경로 버튼 없음.
- 탭 '원내 약도': `floor.svg`(번호 경로가 그려진 그림), `guideSteps` 순서 목록, 다른 이용자 경험(더미) + '참고용 정보' 안내.
- 외부 지도 SDK는 쓰지 않는다(키 확인 전). testid: `hospital-map`, `hospital-floor`, `guide-steps`.

### 15 진료 기록(1단계: 파일 업로드)
- PDF 15쪽의 질문 체크·메모 진입·큰 하단 정리 버튼 배치를 참고한다. 녹음 중 띠·타이머·실시간 자막은 만들지 않고 음성 업로드·변환 상태 카드로 대체한다. 문서 올리기는 T057 선택 전에는 제공하지 않는다.
- 상단 안내: '준비한 진료 음성 파일을 올리면 글자로 바꿔요'. 녹음 허용이 꺼져 있으면 업로드 버튼 비활성 + 문구.
- 진입 시 GET record-input에서 recordInputVersion과 canUploadAudio를 읽는다. canUploadAudio=false면 업로드 버튼 비활성. 전사 성공·메모 저장 후 다시 조회한다.
- 파일 선택 → 업로드 → '글자로 바꾸기'(작업 진행). 결과 화면에는 '변환 완료'와 출처 배지만 보이고 **전사 원문은 full 블록이 있는 정리 결과에서만** 본다.
