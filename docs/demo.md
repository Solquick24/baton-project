# Demo — 로컬 실제 API·fixture·검토 후 공유

2026-10-09 이슈 [#39](https://github.com/Solquick24/baton-project/issues/39). 앱과 실제 API 연결이 구현되어 있다. [분리된 실행법](../specs/001-baton-mvp/quickstart.md)으로 개발 DB/업로드를 보존한다. 기준일은 2026-03-12, 내용은 [seed-story.md](../specs/001-baton-mvp/seed-story.md)의 가상 환자·병원·처방·관찰이다. 전사 입력은 가상 바이트/준비된 fixture이며 실제 음성 인식이 아니다.

## 경로 1: B 이어받기 → C 허용 조회 → A 상세 확인

매 실행 새 격리 시드, B companion/C schedule/A full, 위임false, 내과 질문3개, 3월 진료의 생성/검토/공유본 없음으로 시작한다. 초기 1·2월 내과 기록과 다른 과 기록은 기존 시드 그대로다.

1. B 로그인→가족 질문→통합: 원 질문3→통합2+AI추가1. 이 질문으로 브리핑 생성→변경2·질문3을 정확한 fixture 기대값과 비교한다. B에게 근거/원문 버튼이 없음을 확인한다.
2. 저장 브리핑 GET10회 동안 provider 카운터 증가0을 확인한다. 가상 음성 파일 업로드→fixture 전사→공유 메모 저장→최신 입력 버전 확인→진료 정리 job→ready 검토본을 확인한다. A의 직접 진료 조회에는 새 record가 없다.
3. B가 검토→공유하기→확정. 로그아웃하고 C 로그인→타임라인의 새 schedule 블록을 확인한다.
4. 로그아웃하고 A 로그인→타임라인 상세의 full 내용/근거, 브리핑의 없는 준비사항(null/확인 필요)을 확인한다. 불일치의 저녁/아침 두 근거를 보고 병원 확인 예정으로 처리→새로고침 후 유지한다. 두 근거 중 정답이나 복약 지시를 판단하지 않는다.

## 경로 2: 환자 공개 범위 변경

매 실행 새 격리 시드, B companion, 위임false, 범위 변경 로그0, 생성0으로 시작한다. 환자와 B는 같은 브라우저의 별도 탭에 각자 세션으로 로그인한다.

1. 환자 설정→공개 범위 관리→B 선택. B 탭의 초기 home 내용을 확인한다.
2. schedule 저장→B의 다음 home 응답은 schedule만, 이전 약 이름/질문 진입 제거를 확인한다. full 저장→세 블록, companion 복구→두 블록을 확인한다.
3. B의 직접 PUT 변경은403. B 타임라인은 허용 내용만 있고 원문 버튼이 없다. 환자 공유 기록에는 scope_change3건이 있으며 전체 LLM/STT 호출은0이다.

## 표시·평가·한계

설정의 글씨3단계·고대비·로그아웃·범위 관리 진입을 사용한다. 390px 최대 글씨/고대비 주요20상태의 스크롤 후 조작/잘림을 검사했고, 같은 브라우저 컨텍스트에서 페이지 닫기/재열기 후 설정이 유지됐다. 정적 병원 위치/원내 약도·주소·가상 전화·안내5단계·참고 경험3개는 h_01 시드를 표시하며 지도 SDK/동적 길찾기는 없다.

텍스트 생성·STT는 모두 fixture, 결과 배지는 저장된 대체 결과다. 에이전트의 실제 외부 AI 호출은0회다. 사용자 별도의 단일 OpenAI live/ready/persisted=false 보고는 [최종 체크포인트](final-validation-checkpoint.md)에서 출처를 구분한다.

T065 축소 평가: gold4/4 일치, 정확 문자열 누출 검사 전1/4→blocked 비공개 후0/4, 불일치1/1. 별도 재서술 도전은 탐지0/1 실패. 20장 문서/실제 STT/의료 정확성/전체 live 파이프라인은 미검증이다. Tier C의 녹음·문서 수정·동의/초대/가입 등은 미선택이며 구현/완료로 시연하지 않는다. SC-001~010의 부분 검증·미검증은 최종 체크포인트를 따른다.


추가 진료 동행 노트 안정화 후 다시 완주한 최종 기록이다. 별도 record-flow 브라우저 4건에서 무조작6.6초의 HMR/문서 갱신·자동 job 폴링 부재, 탭 복귀 입력/체크 유지, 메모 성공/실패·폼 DOM/스크롤 유지, 최신 버전으로 정리, 이미 성공한 job 재사용, 검토→명시적 공유→기록 확인, 조회 오류 자동 반복 부재와 권한 철회 시 입력 제거를 검증했다. 실제 OpenAI record 재호출 성공률 검증과 구분한다.
